Three Implementation Approaches

All three end at the same place: SmartDraftPanel on Analyze page → edit params → redirect to /pattern with a saved instance. The difference is how deep the option mapping goes and where intelligence lives.

A

Thin Bridge — wire up what already exists

Add a SmartDraftPanel component to the Analyze page that calls the existing /patterns/auto-draft endpoint (already powered by auto_pattern_maker.py). Render whatever options come back as editable fields. On confirm, save the instance and redirect to /pattern?redraft=....

Option coverage: only what _build_options() currently handles — collarStyle/cuffStyle for simon/simone, kangarooPocket for huey, waistbandWidth for sandy/waralee, elasticWidth for paco. Other designs get SA + ease only.

Pros

  • Smallest diff — mostly frontend work
  • Working in ~1 day
  • No new backend endpoints

Cons

  • Sparse options for 10 of 15 designs
  • Can't show what options were available but not mapped
  • Technical debt — mapping stays incomplete
B

Expanded Rule Mapper — recommended ✦

Significantly expand _build_options() in auto_pattern_maker.py to cover all 15 designs with their key FreeSewing options. Add a dedicated endpoint POST /analyses/{id}/draft-params that returns a full DraftParamsResponse (design, all options, Armstrong metrics, alternatives). SmartDraftPanel renders all options as editable dropdowns/inputs with AI badges.

Option coverage: All major options for all 15 designs — sleeveStyle, pocketStyle, hemStyle, waistbandWidth, paperless, SA, plus design-specific knobs. Each option shows its source: AI-detected vs default.

Pros

  • Full coverage — no design left behind
  • Deterministic, transparent mapping logic
  • No added API cost (pure code)
  • Armstrong metrics already calculated — just expose them
  • Clean API contract for future features

Cons

  • Need to map options for 15 designs (~2–3 days)
  • FreeSewing option schemas must be documented per design
C

AI-Driven Extraction — second Claude call

After Vision analysis, fire a second Claude API call (text only, no image) that reads the structured analysis JSON and directly outputs FreeSewing option key-value pairs: {"collarStyle": "classic", "cuffStyle": "frenchCuff", "sleeveLength": 580, ...}. Claude knows the FreeSewing option schema from a system prompt and can fill options a rule-mapper might miss (e.g. inferred pleat depth, button count).

Option coverage: Potentially any FreeSewing option — Claude reasons from the analysis JSON without hard-coded rules. Can handle unusual combinations that fall through rule gaps.

Pros

  • Highest accuracy for edge cases
  • No need to enumerate every design's options manually
  • Can handle designs added later automatically

Cons

  • Extra API call = extra latency (1–2s) + cost per analysis
  • Non-deterministic — can produce different options for same photo
  • Harder to debug and explain to users why a value was chosen
  • Overkill given the rule system is already 80% there
Why B is recommended

auto_pattern_maker.py is already well-structured — _DESIGN_OPTION_MAP just needs expanding. The Armstrong metrics are already computed and just need a UI surface. Rule-based mapping is transparent (user can see why each option was chosen), free to run, and deterministic. Approach C could be added later as a fallback for options that rules miss.
